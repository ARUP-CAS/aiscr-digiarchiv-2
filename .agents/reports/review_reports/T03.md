# T03 — Analysis of Solr schemas, configurations, and indexing patterns

**Date:** 2026-03-08
**Scope:** 14 Solr configsets, Java indexing code, SolrSearcher, FedoraHarvester

---

## Summary of findings

The repository contains 14 Solr configsets. The main collection is `entities` with more than 330 explicit fields covering all AMČR record types (dokument, akce, lokalita, projekt, samostatný nález, ADB, 3D model). The Java indexing code is split into:
- `FedoraHarvester.java` (1024 lines) — full and incremental indexing from the Fedora API
- `IndexUtils.java` — helper methods for writing to `SolrInputDocument`
- `SolrSearcher.java` (1048 lines) — query logic + faceting
- Dozens of model classes `fedora/models/*.java` — mapping AMČR entities to Solr fields

Indexing is **incremental**: FedoraHarvester.update() queries the Fedora REST API for records with `modified >= lastDate`. Full reindexing is triggered via `harvest()` or `indexModels()`.

The client library is `Http2SolrClient` (solr-solrj 9.10.1), while the Solr server configuration declares `luceneMatchVersion=9.4` — a mismatch with the client.

## Identified problems

### Critical defects

| ID | Severity | File | Description |
|----|-----------|--------|-------|
| SOLR-001 | **Critical** | `solr/entities/conf/managed-schema:157` | Typo `multiValued="fslse"` on the field `samostatny_nalez_projekt` — invalid boolean attribute value |

**SOLR-001 detail:** Solr receives `fslse` as an invalid value. The behavior is undefined and depends on the Solr version — it may cause unexpected multi-valued behavior or record indexing failure.

---

### High severity

| ID | Severity | File | Description |
|----|-----------|--------|-------|
| SOLR-002 | High | `solr/*/conf/solrconfig.xml:38` | `luceneMatchVersion=9.4` vs. `solr-solrj=9.10.1` — all 14 collections |
| SOLR-003 | High | `solr/entities/conf/managed-schema:622` | `BoolField` without `docValues=true` — boolean filtering is slower |
| SOLR-004 | High | `FedoraHarvester.java:263` | `max_results=10000000` without pagination — OOM risk during full indexing |
| SOLR-005 | High | `SolrSearcher.java:566` | `setRows(100000)` for ruian_katastr without overflow verification |

**SOLR-002 detail:**
All `solrconfig.xml` files have `<luceneMatchVersion>9.4</luceneMatchVersion>`, while the `solr-solrj` client is at version 9.10.1. When a Solr 9.10 server is deployed with luceneMatchVersion=9.4, the Lucene 9.5–9.10 optimizations are not activated. Additionally, there is a risk that reindexing runs with different version-specific tokenizer/analyzer behavior.

**SOLR-004 detail:**
```java
// FedoraHarvester.java:260-265
int max_results = 10000000;
String s = FedoraUtils.search(baseQuery + "&include_total_result_count=true&offset="
    + pOffset + "&max_results=" + max_results);
JSONObject json = new JSONObject(s);  // entire response in memory!
```
If Fedora returns hundreds of thousands of records, the whole JSON is loaded into the heap. `checkDatestamp()` in the same class correctly uses cursor-based iteration — but `indexModels()` does not.

### Medium severity

| ID | Severity | File | Description |
|----|-----------|--------|-------|
| SOLR-006 | Medium | `managed-schema:666` | `rdate` (DateRangeField) without `docValues` — project dates cannot be sorted or faceted |
| SOLR-007 | Medium | `managed-schema:116 vs. :342` | `az_dj_nazev` commented out as `string`, the active field is `text_general` — incomplete refactoring |
| SOLR-008 | Medium | `solr/oai/conf/managed-schema.xml` | Different file extension `.xml` vs. other collections without an extension |
| SOLR-009 | Medium | `DokumentSearcher.java:94`, `AkceSearcher.java:139`, `ProjektSearcher.java:85..307` | `setRows(10000)` without pagination — memory risk with a larger database |

**SOLR-006 detail:**
Fields like `projekt_datum_zahajeni` are defined as `rdate` (DateRangeField) because they allow range interval values (e.g. "2020/2021"). However, `DateRangeField` does not support `docValues` in Solr — which means:
1. These fields cannot be used for sorting
2. Numeric faceting (stats) on them works with reduced performance

| Record type | Java class | Collection | Field prefix |

Access rights are modelled using a **suffix strategy**: protected data is indexed into fields with the suffix `_A`, `_B`, `_C`, `_D` according to the accessibility level (`IndexUtils.addSecuredFieldNonRepeat()`). The fulltext fields `text_all_A..E` are populated programmatically in `ArcheologickyZaznam.setFullText()`, not via `copyField`.

## Indexing trigger

```
Incremental:
  FedoraHarvester.update(from, until)
    → Fedora REST API: /fcr:search?condition=modified>={from}
    → Batch processing (batchSize=1000)
    → Commit after each batch
    → Stores the timestamp in update_time.txt

Full reindexing:
  FedoraHarvester.harvest()
    → Runs update() from the oldest datestamp in Solr
  FedoraHarvester.indexModels(String[] models)
    → PROBLEM: max_results=10M without pagination
```

## Improvement proposals

### 1. Immediate fix (1–2 days)
- Fix the typo `multiValued="fslse"` → `"false"` (SOLR-001)
- Rename `oai/conf/managed-schema.xml` → `managed-schema` (SOLR-008)
- Add `docValues="true"` to `BoolField` in all collections (SOLR-003)

### 2. Short-term improvement (1–2 weeks)
- Update `luceneMatchVersion` to a version matching the Solr server; then full reindexing (SOLR-002)
- Refactor `indexModels()` — add cursor-based pagination (SOLR-004)
- Add a `numFound <= rows` check in `getAllKatastry()` (SOLR-005)
- Replace `copyField source="*"` with explicit fields in heslar and soubor (SOLR-010)

### 3. Medium-term improvement (1–3 months)
- For sort/facet on project dates, add duplicate `pdate` fields alongside the existing `rdate` (SOLR-006)
- Refactor the `setRows(10000)` queries to cursor pagination in all Searcher classes (SOLR-009)
- Document the intentional comments in the schema (SOLR-007)
- Consider field-level security for the uzivatel collection (SOLR-011)
