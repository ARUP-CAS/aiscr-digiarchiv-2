## 1. Summary of findings

The repository contains the production web application **Digitální archiv AMČR** (AMCR Digital Archive) — the presentation layer for AIS CR archaeological data. The architecture consists of four main components:

1. **Java/Servlet backend** (`web/`) — 88 Java classes organized into 5 packages. The application
   communicates with the Fedora Repository REST API for reading data and with Apache Solr for search.
   Packaging is WAR (deployed to a servlet container, most likely Tomcat).

2. **Angular frontend** (`web/src/main/ng/`) — a TypeScript/Angular SPA built by a Maven plugin
   as part of the WAR archive. It contains components, pages, shared utilities, and SCSS styles.

3. **Apache Solr** (`solr/`) — 14 collections covering different data types. Search is a key
   function of the system; each AMČR record type has its own Searcher class.

4. **ThumbnailsGenerator** (`ThumbnailsGenerator/`) — a standalone Maven module for batch
   generation of image and PDF thumbnails from the Fedora Repository and their indexing into Solr.

The system implements the OAI-PMH protocol for metadata harvesting and supports multiple AMCR API
versions (v2.0, v2.1, v2.2) via XSLT transformations.

## 2. Identified problems

### P01 — Absence of automated tests
- **Finding:** The `web/src/test` directory does not exist. The project has no automated Java tests.
- **Impact:** Regressions cannot be detected automatically; the CI pipeline cannot verify
  code correctness before deployment.
- **Severity:** High

### P02 — Typo in a Java package name
- **Finding:** The package `cz.inovatika.arup.digiarchiv.web4.imagging` contains a typo
  (`imagging` instead of `imaging`).
- **Impact:** The typo propagates through imports and is visible in documentation. Fixing it requires
  renaming the package and all imports.
- **Severity:** Low (cosmetic, but confusing)

### P03 — Inconsistent base package in ThumbnailsGenerator
- **Finding:** ThumbnailsGenerator uses `cz.incad.arup.thumbnailsgenerator`, while the
  main application uses `cz.inovatika.arup.digiarchiv.web4`. The different organization (`incad` vs
  `inovatika`) suggests the module historically has a different origin.
- **Impact:** Makes it harder to navigate the codebase and understand code ownership.
- **Severity:** Low

### P04 — Missing managed-schema for the `oai` collection
- **Finding:** The `solr/oai/conf/` collection does not contain a `managed-schema` file, which all
  other collections have.
- **Impact:** It is unclear whether the collection uses a default schema or dynamic fields. Risk of
  unexpected behavior during indexing.
- **Severity:** Medium — to be investigated in more detail in T03.

### P05 — Missing Docker/infrastructure configuration
- **Finding:** There are no Dockerfile or docker-compose files in the repository.
  Infrastructure configuration probably lives in an external repository or is in `.gitignore`.
- **Impact:** The application cannot be run locally from this repository without additional resources.
  Complicates onboarding of new developers.
- **Severity:** Medium

### P06 — 14 Solr collections without an apparent consolidation strategy
- **Finding:** The system uses 14 separate Solr collections. 10 of them share an identical
  `solrconfig.xml`, which suggests it was copied without customization.
- **Impact:** Managing and updating the configuration is harder; a change in `solrconfig.xml` must
  be applied to 10 files.
- **Severity:** Medium

## 3. Improvement proposals

1. **Tests:** Add at least basic unit tests for key classes (SearchUtils, IndexUtils,
   FormatUtils, FedoraUtils). Consider integration tests for Solr queries.

2. **`imagging` typo:** Rename the package to `imaging`. Can be done automatically in an IDE
   (refactor → rename package) with all imports updated.

3. **Solr `solrconfig.xml`:** Consider using Solr configset inheritance, or maintain a shared
   `solrconfig.xml` in one place with symlinks/sharing via CI.

4. **Docker configuration:** Document in the README where the infrastructure configuration
   (docker-compose) lives, or consider adding a development `docker-compose.yml` directly to the repository.

5. **`oai` collection:** Verify whether the absence of `managed-schema` is intentional (dynamic schema)
   or an error. Add a comment to `solrconfig.xml`.
